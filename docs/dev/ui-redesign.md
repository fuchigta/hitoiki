# UI 再設計の計画（オブジェクト指向 UI）

GUI の情報設計をオブジェクト指向 UI（OOUI）で見直すための計画です。現状の棚卸し、目標の構造、段階的な移行の順序、各段階での確かめ方を書きます。実装が進んだら、この文書を更新するか、`architecture.md` に吸収して消します。

確かめ方の道具（モック IPC・スクリーンショット巡回）は [development.md](./development.md) の「UI の確認（モックとスクリーンショット）」にあります。

## 実装状況

P0〜P6 は実装済みです（§4 の各段階。ナビは「今日 / 実績 / タスク / 目標 / 記録 / レポート / 設定」の順で、「はじめに」はナビ外）。§1 の問題は、下の「計画から変えた点」を除いて解消しています。計画から変えた点は次のとおりです。

- **ルールの行部品の完全な共通化は未実施。** 設定の「ルール」は帰属・活動・無視を 1 つの一覧にしましたが、タスク詳細の「ルール」タブの行と設定の行は、`rule-row.tsx` の部品を共有しつつ、フォームは別々のままです。
- **選択状態を URL に載せないものがある。** ルートに載るのはタスク・成果の指標・スキル・区間（実績）・記録・設定のタブ・今日の日付と `design` です。設定の「ルール」で選んでいるルール、今日のサイドパネルで開いているブロック・区間・付け替え・未回答の問いかけは載りません（日付の移動だけがブラウザの戻る・進むでたどれます）。
- **旧名の受け方。** `review`・`plan`・`reflect` は SCREENS から外して `LEGACY_IDS` に入れ、`legacyRoute` が新しいルートへ写します。`checkin`・`hassle`・`reflection` は、`routeFromHash` が記録・振り返りの形に寄せてから `legacyRoute` が仕上げます。Rust 側の `SCREENS` は旧名も受け付け、写像は UI に任せています。
- **今日のサイドパネルは同時に 1 つ。** ブロック・区間・付け替え・問いかけは、開くと入れ替わります。今日のデザインは「完了」まで保ち、別のパネルを閉じるとデザインに戻ります（`today-util.ts` の `sideReducer`）。`DayGrid` のポップオーバーはなくなりました。
- **テンプレートの保存は今日のデザインだけ。** 設定のテンプレートタブは管理（作成・編集・削除）だけで、見ている日の配置の保存はサイドパネルのデザインから行います。
- **今日以外の日の合計・内訳。** 今日は `status` の集計、それ以外の日はレポート API（`report`）と区間の合計から出します。
- **ブラウザの戻る・進むのガード。** 未保存の変更があるとき、`lib.ts` が 1 つだけ持つ `hashchange` のリスナーが元のハッシュに戻して `leaveGuard` の確認を出します（判定は `hash-guard.ts` の純粋関数）。

## 1. 現状の問題

2026-10-13 時点のスクリーンショット（`npm run shots`）とコードの棚卸しから分かったことです。

### 情報設計（OOUI の観点）

1. **ナビが作業名（動詞）で分かれている。** 「仕分け」「計画」「振り返り」「記録」「レポート」は作業の名前です。ユーザーは「どの画面で何をするか」を覚える必要があります（`ui/src/lib.ts` の SCREENS）。
2. **実績（区間）に居場所がない。** 区間は今日のタイムライン、仕分け、計画の「計画と実績」、補正パネル、タスク詳細の「補正した時間帯」、レポートに散らばっています。「要確認」は区間の状態（属性）なのに、独立した画面になっています。
3. **ブロックの画面が 2 つある。** 今日と計画が同じ `DayDesigner` を持ちます。計画では、同じブロックを下にもう一度一覧で出しています（`Plan.tsx:65-78`）。
4. **同じ関係を両側から編集できる。** タスクと成果の指標の紐付けは、タスク詳細（`KeyResultPicker`）と成果の指標カード（`KeyResultTasks`）の両方で編集できます。スキルの付け外しも 3 か所です。
5. **ルールが 3 種類に分かれ、置き場所も別々。** 帰属ルールはタスク詳細、活動ルールと無視するアプリは設定にあります。同じ形のフォームと行の部品が 2 系統あります（`Tasks.tsx:439-473` と `data-settings.tsx:36-62`、`rule-row.tsx`）。無視の入口は 5 か所あります。
6. **記録の画面が入力フォームの集まりになっている。** チェックイン・ハッスル・ABC の入力フォームが常に開いていて、一覧はその下です（カードが 8 枚）。振り返りは同じ「自分の記録」なのに別の画面で、ERG の分布も 2 か所にあります。
7. **仕分けが「全件フォームの繰り返し」になっている。** 1 区間ごとに入力 3 つとボタン 5 つが並びます。一括バーも同じ入力を持っています（`Review.tsx:176-421`）。仕分けのタスク選択だけが、検索できない `<select>` です。
8. **目標画面で全成果の指標が常に開いている。** 集計・週別バー・履歴・提案・スキル・タスク・追加フォームが成果の指標ごとに展開されます。成果の指標が 4 つでも縦 3000px を超えます。
9. **設定に、単純な設定値とオブジェクトの一覧が同じ階層で並ぶ。** 「仕分け」カードには通知（`push.*`）の閾値が混ざっています。オンボーディングは、自動起動・`trust_doing` などの設定を別に実装し直しています。

### 見た目（ごちゃごちゃして見える原因）

- **余白・文字サイズ・角丸がトークンになっていない。** font-size は 13 種類（px と em が混在）、border-radius は 9 種類あります。余白はすべて px の直書きです。
- **強調の手段が多すぎる。** `<strong>`、`.big`、`.primary`（仕分けの 1 画面に 4 か所）、`.tag`、`.chip.on`、`.attn` が混在しています。
- **説明文（`.muted`）が多く、意味が区別されていない。** 補足・日時・状態・ヘルプがすべて同じ灰色です。今日の画面だけで 15 か所あります。
- **行ごとに「編集」「削除」のボタンが並ぶ。** 設定の活動ラベルは 9 行 × 2 ボタンです。
- **見出しが h1 と h2 だけ。** カードの階層がなく、全部が同じ `.card` に見えます。
- **CSS の不具合がある。**
  - `styles.css` の `.erg-dist li` の閉じ括弧が抜けています。そのため後ろの `.heatmap*` が入れ子になり、レポートのヒートマップと成果の指標の週別バーが崩れています。
  - `.chip` が 2 か所で定義されています（277 行・843 行）。フィルタの chip まで grab カーソルになり、`on` の見た目が 2 通りあります。

## 2. 目標の構造

### オブジェクトとナビ

ユーザーが認識する名詞を、そのままナビの項目にします。作業（動詞）は、オブジェクトを選んでから行う操作か、一覧の絞り込みにします。

| ナビ | 主オブジェクト | 吸収する現行画面・部品 | 主な操作 |
|---|---|---|---|
| **今日**（`today`） | 1 日（予定・ブロック・実績を並べた入れ物） | 今日、計画、今日のデザイン、テンプレートの適用 | 日付の移動、ブロックの作成・移動、範囲を選んで付け替え |
| **実績**（`log`） | 区間 | 仕分け、補正パネル、ルール化・無視の提案 | 絞り込み（要確認・タスクなし・期間）、割り当て、無視 |
| **タスク**（`tasks`） | タスク | タスク、クイック入力の作成先 | 作成、状態の変更、編集、削除 |
| **目標**（`goals`） | 目標 / 成果の指標、スキル | 目標・スキル | 作成、編集、値の記録、紐付け |
| **記録**（`records`） | チェックイン、ハッスル、ABC、振り返り | 記録、振り返り、未回答の問いかけ | 作成（種類を選ぶ）、編集、ERG の確定 |
| **レポート** | 集計（実体なし） | レポート、ヒートマップ | 軸と期間の切り替え、項目からオブジェクトへ移動 |
| 設定（下端） | 設定値、ルール、ラベル、カレンダー、テンプレート | 設定、オンボーディングの設定部分 | 変更 |

- 「要確認 N 件」と「未回答の問いかけ」は、ナビの**バッジ**と今日のヘッダーに出します。独立した画面にはしません。
- 「はじめに」はナビに出さない現状のままにします。設定の部品を再利用し、実装の二重化をなくします。

### 画面の型（3 種類に揃える）

1. **一覧＋詳細（List–Detail）**: 時間・タスク・目標・記録・設定のルール。
   - 左に一覧（絞り込み・並べ替え・「＋」で作成）、右に選んだオブジェクトの詳細を置きます。
   - 操作は詳細の中にまとめます。一覧の行にはボタンを置かず、状態と要点だけを出します。
   - 複数を選ぶと、詳細の位置に**同じ編集パネル**が「N 件を選択中」として出ます（仕分けの一括バーと各カードの二重実装をなくす）。
2. **時間軸（Timeline）**: 日。
   - 予定・計画・実績の 3 列を残します。
   - ブロックか区間をクリックすると、右の詳細パネルに**一覧＋詳細と同じ部品**で出ます。ブロックは BlockForm、区間は時間の詳細、範囲選択は付け替えです。
3. **集計（Report）**: レポート。
   - バーやヒートマップのセルから、対象オブジェクトの詳細へ移動できるようにします。

### 関係の正本を決める

関係は**持ち主の側でだけ編集**し、反対側は参照（リンク付きのチップ）にします。

| 関係 | 編集する側 | 参照する側 |
|---|---|---|
| タスク → 成果の指標 | タスクの詳細 | 成果の指標の詳細（タスクの一覧。「タスクを紐付ける」はタスク詳細を開く導線として残す） |
| タスク → スキル | タスクの詳細 | スキルの詳細 |
| 成果の指標→ スキル | 成果の指標の詳細 | スキルの詳細 |
| タスク ← 帰属ルール | 設定 › ルール（種類で絞り込み） | タスクの詳細（そのタスクのルールを同じ行部品で表示し、追加はその場で可） |
| 区間 → タスク | 実績の詳細 | タスクの詳細（「時間」タブ。補正もここ） |
| ブロック → テンプレート | 設定 › テンプレート | 今日（適用だけ） |

### 作成の入口

- 各一覧の「＋」を正規の入口にします。
- その場での作成（`TaskPicker` の「新規作成: …」、クイック入力）は残します。ただし作成ロジックは 1 つの関数にまとめ、作ったあとは「タスクを開く」へのリンクを出します。
- 仕分けの `<select>` は `TaskPicker` に置き換えます。

### ルート

一覧で選んだオブジェクトは URL のハッシュに載せます（例 `#/tasks/<ID>`、`#/goals/key-result/<ID>`、`#/log/<区間ID>`、`#/records/<種類>/<ID>`、`#/settings/<tab>`、`#/today?date=YYYY-MM-DD`）。戻る・進むで選択も戻ります。

### 互換性（変えてはいけない入口）

`hitoiki ui <画面>`、トレイ、通知の `open_screen`（例 `reflection/day_end`、`today/design`、`records`）、起動引数 `--screen review` が、既存の画面名を使っています。

- 新しいルートに移っても、`lib.ts` の `screenFromHash` で旧名を新ルートへ写します。例: `review` → `log?status=review`、`plan` → `today`、`reflect/day_start` → `records/new/day_start`。写像は `legacyRoute`（純粋関数）にして vitest で検査します。新しい画面 ID（`log`）は Rust 側の `normalize_screen` にも足します。
- `docs/user/cli.md` の画面名の表は、旧名を受け付けることを明記したうえで、新しい名前を足します。
- CLI でできることは変えません（GUI だけの再編です）。

## 3. 見た目の基礎（デザイントークンと部品）

情報設計の変更より先に入れて、各段階で使います。

- **トークン**（`:root`）
  - 余白: `--sp-1..6` = 4/8/12/16/24/32
  - 文字: `--fs-xs/s/m/l/xl` = 12/13/14/16/20、数字の強調だけ 28
  - 角丸: `--r-s/m/pill` = 4/8/999
  - 影は 1 種類
- **ボタンの階層**
  - primary は 1 つの画面に 1 つ（その文脈の主操作）。
  - secondary と ghost を使い分ける。
  - 破壊的な操作（削除・外す）は詳細の末尾か、行の「…」メニューに入れる。
- **文字の役割**: 本文・補足（`--muted`）・メタ情報（時刻・件数。等幅数字）・ヘルプを区別します。常に出しているヘルプ文は、空の状態の案内か「?」のツールチップに移します。
- **共通部品**（`components.tsx` に集約）
  - `ListDetail`、`ObjectList`、`DetailPanel`
  - `Section`（h2 / h3 の階層）
  - `EmptyState`、`OverflowMenu`
  - `PeriodSelect`（期間の選択肢を 1 か所で定義）
  - `Scale`（1〜5。4 つある実装を 1 つに）
  - `ConfirmDelete`（`Tasks.tsx` の独自の `DeleteTask` も寄せる）
- **オブジェクトの見分け**: 種類ごとの小さなアイコンかラベル色（タスク・区間・ブロック・成果の指標・記録）を、一覧・チップ・詳細の見出しで共通にします。

制約に関わる注意: 時間の使い方に良し悪しの評価をつけない（AGENTS.md）。ヒートマップや進捗の色・文言を変えるときは、「多い／少ない」「達成／未達」を良し悪しに見せる表現（赤・警告色など）を使いません。

## 4. 段階的な移行

各段階は単独でリリースできる大きさにします。段階ごとに `docs/user/daily-use.md` と `CHANGELOG.md` の `[Unreleased]` を更新します（`ui/src/screens/**` を変えると doc-sync の検査が要求します）。

| 段階 | 内容 | 主に触るもの | 規模 |
|---|---|---|---|
| **P0 確かめる仕組み** | モック IPC・スクリーンショット巡回（済）。操作のシナリオ（§5 の L3）を追加。CSS の 2 つの不具合を直す | `ui/src/dev/`、`ui/scripts/`、`styles.css` | 小 |
| **P1 見た目の基礎** | §3 のトークンと共通部品。行のボタンを「…」に。説明文を減らす。ボタンの階層を揃える。**画面構成は変えない** | `styles.css`、`components.tsx`、各画面の置き換え | 中 |
| **P2 一覧＋詳細：タスク・目標** | タスク詳細をタブ（概要／時間／ルール）に。目標は成果の指標を一覧にし、選んだものだけ詳細を開く。関係の編集を正本の側に寄せる | `Tasks.tsx`、`Okr.tsx`、`key_result-*.tsx` | 中 |
| **P3 実績** | 仕分けを「実績」（要確認を既定の絞り込み）に置き換える。区間の詳細パネルを、今日のタイムラインのクリック・範囲選択（補正）・複数選択で共用。無視とルール化は詳細の中と提案カードだけに | `Review.tsx`→新画面、`correction.tsx`、`day-grid.tsx` | 大 |
| **P4 今日** | 今日と計画を「今日」に統合（日付の前後移動、今日はヘッダーに「いま」と合計）。今日のデザインは右パネルのモードに。テンプレートの管理は設定へ | `Today.tsx`、`Plan.tsx`、`day-designer.tsx`、`templates.tsx` | 大 |
| **P5 記録** | チェックイン・ハッスル・ABC・振り返りを 1 つの時系列にし、「＋記録」で種類を選ぶ。ERG は詳細の属性、確認待ちは絞り込みに。未回答の問いかけは今日のヘッダーと記録の両方から開く（同じ `PushAnswer`） | `Records.tsx`、`Reflect.tsx`、`record-edit.tsx`、`reflect-form.tsx` | 大 |
| **P6 設定** | 一般／通知／クイック入力／判定の閾値（設定値）と、ルール（帰属・活動・無視をまとめた一覧）、ラベル、カレンダー、テンプレート（オブジェクト）をタブで分ける。オンボーディングは同じ部品を使う | `Settings.tsx`、`data-settings.tsx`、`rule-row.tsx`、`Onboarding.tsx` | 中 |

順序の理由:
- P1 を先にやると、画面構成を変える前でも、ごちゃごちゃした印象のかなりの部分が減ります。
- P2 で「一覧＋詳細」の部品を、比較的単純なタスクで固めます。最も複雑な P3（区間）と P4（日）は、その部品を使い回します。
- P3 は P4 より先にやります。区間の詳細パネルができていれば、日のタイムラインからはそれを開くだけになります。

依存がない段階（P5 と P6 など）は、別のワークツリーで並行して進められます。

## 5. 確かめ方

実装する人（人でも AI エージェントでも）が、各段階で次を通します。

| 層 | 何を見るか | 道具 | いつ |
|---|---|---|---|
| L1 ロジック | `*-util.ts` の純粋関数（絞り込み、正規化、画面名の写像など） | vitest（`npm test`） | 常に。旧画面名 → 新ルートの写像は必ずテストを書く |
| L2 見た目 | 全画面 × シナリオ（default / empty / busy）× ライト・ダークのスクリーンショット | `npm run shots`（モック IPC + Playwright。Edge / Chrome を使い、ブラウザはダウンロードしない） | 画面を変えるたび。AI エージェントは PNG を Read して確認する |
| L3 操作 | 「区間を選ぶ → タスクを割り当てる → 一覧から消える」のような主要な流れ | Playwright のスクリプト（`ui/scripts/flows/`、role と名前で要素を選ぶ）。モックの状態 `window.__mock.state` で結果を検証 | P0 で主要な 5 本程度を作り、段階ごとに足す |
| L4 差分 | 意図しない見た目の変化 | 前回の撮影結果と比べる（`--diff`。pixelmatch（ISC）で差分画像を出す）。基準画像はリポジトリに入れない | P1 以降、リファクタの段階で |
| L5 構造 | 見出しの階層、ボタンの名前、ランドマーク | Playwright の `ariaSnapshot()` をテキストで保存して差分を見る | P1 以降 |
| L6 実機 | Tauri の実ウインドウ、通知、トレイ、クイック入力のショートカット | 人が `hitoiki-app` を起動して確認 | 各段階の最後 |

- axe-core は MPL-2.0 で、依存の方針（permissive のみ）に合わないため使いません。アクセシビリティは L5 の構造の確認で代えます。
- モックは本番のビルドに含めません（`vite --mode mock` のときだけ動的に読み込む）。新しい Tauri コマンドを足したら、モックのハンドラにも足します（`mock.test.ts` が網羅を検査します）。
- 判断の基準（L2 で見るもの）
  - 1 画面の primary ボタンは 1 つか。
  - 常に出ている説明文が増えていないか。
  - empty シナリオで空の状態の案内が出るか。
  - busy シナリオで長い名前が崩れないか。
  - ダークモードで読めるか。
