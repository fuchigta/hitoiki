# Kani による形式検証は採用しない

hitoiki-core の時刻計算を対象に、形式検証ツール Kani（0.68.0）の導入を試行した（PR #13）。`day_range` の7つの主張を UTC と Asia/Tokyo の2タイムゾーン、2000年から2099年の全日付（36,525通り）で検証する14ハーネスを作り、すべて検証成功した。しかし、この試行の範囲では担保される品質に対して作成と CI のコストが釣り合わないため、採用は見送る。

釣り合わないと判断した理由は次の3点。

- 検証できた範囲は有限で列挙可能だった。全日付でも36,525通りしかなく、通常のテストで全数を数秒で確認できる。Kani の強みが出る列挙できない空間（時刻の往復変換の全範囲）は、30分でも検証が終わらなかった。
- 対象は UTC と東京という、サマータイムがなく時差も切りが良い、時刻計算の中で最も易しい断片だった。この範囲は既存の proptest でも十分にカバーされている。
- 継続コストが大きい。ハーネス1件のコード生成に約3GBのメモリを使い、CI ではハーネスごとにジョブを分けて並列実行しても約11分かかる。試行時のワークフローにはパスフィルタがなく、時刻計算に触らない PR でも毎回この時間がかかる構成だった。

## Consequences

- PR #13 はマージせずに閉じる。検証モジュールと `kani.yml` は main に入れない。
- 時刻計算の品質担保は、引き続き proptest のプロパティテストと通常のテストで行う。
- 再検討する条件：往復変換のような列挙できない空間を、補題の分解や関数の事前・事後条件で証明できる見通しが立ったとき。その場合も、対象を絞り、ワークフローにパスフィルタを付けて狭く始める。
